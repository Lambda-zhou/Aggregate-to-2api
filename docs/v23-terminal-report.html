① 上下文 / 为什么做 v23

v22.1.5 基线已把版本门禁、i18n、PWA、SSE 连接保护、移动端冒烟等工程项闭环。v23 面对的是三个此前从未被正视的真实缺口：

  • 「线上无 Docker」被 v22 指南忽略：v22 的 litestream/观察栈/solver 双节点全按 docker compose 写，但生产 20.204.27.154 是 systemd 原生直跑——文档路径不可能执行，RPO 24h 兜底名存实亡；
  • 版本基线脱节：代码全链 22.0.0，Release 已发到 v22.1.5——每个 patch 只 tag 版本未 bump 全链；
  • 盲点未扫：从未启动过"最挑剔用户/最倒霉调用方/最狠反对者"视角的纵深审计——SQL 慢查询、日志脱敏、鉴权边界、前端假加载全是空白。

本轮 = 一次真正的终局闭环总审计：7 个并行/串行子代理节点（契约 50 端点 / SQL 27 文件 / 安全 / 前端 13 页 / solver 实测 / 部署 / 独立审查）全链路伸展开，发现问题 → 修复 → 复验 → 版本发布。

⑥ v23.1 增补：极限施压 + 防穿透 + 覆盖率猎杀（Spec-Kit 011）

触发：`.specify/specs/010` 的 US2「高并发极限施压探针」只有 spec 无 plan/tasks——承诺未兑现；用户点名「极限施压与防穿透」「覆盖率看着 80% 仍出 bug」。

节点结果
T1 极限施压读路径（healthz/gallery/stats/providers/models）200 并发 0 错误率、0 5xx、0 429、进程不崩；延迟 16-40ms（串行）→ 100-600ms（并发，本机 HTTP 排队噪声双口径标注）
T2 防穿透畸形 JSON/超长 prompt(200KB)/5MB body 全 422 不崩；生图限流 10→5 个 429 + Retry-After:60；auto-block 403 实测（task-failure-burst 机制真实生效 = S-2 生产核对项实证）
T3 覆盖率猎杀v23 修复模块基线仅 61.5%（log_buffer 43.2% / auth 65.9% / alerting 62.1%）——"看着 80% 仍出 bug"实证
T4 补测auth→76.1% / alerting→95.4% / log_buffer→88.9%；顺带抓出真实 bug：`attr_custom` 被 `k[6:]` 错剥成 `ustom`，已修
T6 独立审查首轮 NEEDS_CHANGES（F1 429 误判崩溃 P1 + F2-F8）→ 全部修复 → 复验 APPROVE（36 补测 + 编译 + ruff 0 error）

根因模式：工具本身也需防穿透——压测探针把 429（优雅降级）误判为崩溃阈值，反过来会把"限流保护生效"报成"服务挂了"。独立审查抓出并修复（F1）。
